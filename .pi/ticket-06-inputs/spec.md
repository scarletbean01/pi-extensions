# Persistent Bootstrap software factory

Status: ready-for-agent

## Problem Statement

Running the same Bootstrap workflow for each new brief takes repeated setup and supervision. A run is a one-off graph: it does not accept another brief after finishing, keep a queue across Pi sessions, or durably ask a person to direct a decision. When a launch or a response is interrupted, an operator needs to tell what was recorded, what may have executed, and whether it is safe to proceed without duplicating work or reusing a checkout that is still busy.

## Solution

A software factory is a named, persistent entry point to a Bootstrap graph. In the managing Pi session in Herdr, an operator publishes a definition, submits plain-text briefs, and receives a durable receipt for each accepted input. The factory launches a separate run per input, in acceptance order and only when capacity is safe to use. Enabled agents can ask for human direction; a plan-defined routing choice can approve a decision node or request a bounded revision. A compact Pi view surfaces requests and blockers, with detail on what was accepted, what ran, and what actions are safe. The factory can be stopped and explicitly resumed or taken over without cancelling its runs or replaying uncertain work.

## User Stories

1. As an operator, I want a stable factory ID, so that I can return to the same factory when its definition changes.
2. As an operator, I want to open a factory without resuming it, so that inspection does not start work.
3. As an operator, I want to explicitly resume management, so that a new Pi session does not start launching unexpectedly.
4. As an operator, I want to stop new admissions and launches without cancelling runs, so that accepted work is preserved for later.
5. As an operator, I want to take over when the managing session disappears, so that I can recover without competing managers.
6. As a graph author, I want to validate and explicitly publish a definition without launching, so that mistakes do not affect work already accepted.
7. As a graph author, I want publication errors to identify the failing node, setting or prerequisite where known, so that I can fix the definition.
8. As an operator, I want current and bound versions shown separately, so that I can explain why an input uses an older graph.
9. As an operator, I want to see which settings inherit Pi's runtime defaults, so that I know which parts of the environment were not frozen.
10. As an operator, I want to publish a preserved version as a new version, so that I can restore old behavior without rewriting history.
11. As a submitter, I want to paste a multiline brief through a direct Pi command, so that ordinary chat is never mistaken for work submission.
12. As a submitter, I want an acceptance receipt before a run exists, so that I know the factory has recorded my input even while busy.
13. As a submitter, I want a submission reference before the write, so that I can look up or retry the submission if I lose the acknowledgement.
14. As a submitter, I want reuse of a reference to detect a changed brief, so that retry cannot silently change accepted work.
15. As a submitter, I want a new reference to allow the same brief again, so that intentional repetition is not deduplicated by content.
16. As a submitter, I want invalid, oversized or excess submissions rejected with reasons, so that accepted work is never silently dropped.
17. As an operator, I want to discard an input only before launch begins, so that I can correct the queue without mistaking discard for cancellation.
18. As an operator, I want a discarded input's receipt retained, so that a retry cannot revive it.
19. As an operator, I want launch order to follow durable acceptance order, so that a blocked head cannot be skipped silently.
20. As an operator, I want to distinguish a routine wait from a checkout conflict, version block or uncertain hold, so that I know whether I need to act.
21. As an operator of two factories, I want them to coordinate when targeting the same checkout, so that aliases and separate Herdr workspaces do not allow overlapping runs.
22. As a graph author, I want existing within-run parallelism and ownership checks preserved, so that serial factory inputs do not serialize the entire graph.
23. As a graph author, I want to opt in particular nodes and define their choices, so that agents cannot invent routes.
24. As an enabled agent, I want to request direction when I need it, so that I do not need to guess or interrupt every attempt in advance.
25. As an operator, I want a prominent alert and a persistent intervention list, so that a missed alert does not leave me unaware of a waiting attempt.
26. As an operator, I want to see the question, context, evidence, choices and recommendation if present, so that I can make an informed choice.
27. As an operator, I want to select a choice or explicitly decline, with optional guidance, so that silence and free text are not mistaken for a route.
28. As an operator, I want to retry an identical response safely, so that a lost acknowledgement cannot cause two continuations.
29. As an operator, I want to see whether my response was recorded, consumed, reflected in a verdict, and followed by admission, so that I know what actually happened.
30. As an enabled agent, I want a human wait not to consume my execution timeout, so that the operator can answer at their own pace.
31. As a graph author, I want dependants not to time out solely because of a human wait while unrelated work keeps its own deadlines, so that the run honors both operator input and graph limits.
32. As an operator, I want a selected route to bind the attempt without bypassing result contracts or checks, so that approval does not admit invalid work.
33. As an operator, I want a revision to revisit the declared loop body on the same agents, so that the existing review budget and context are preserved.
34. As an operator, I want to see what an exhausted revision choice will do, so that rejection cannot silently become approval or start part of a revision.
35. As an operator, I want an approval at a terminal decision node to finish its branch only, so that independent work is neither cancelled nor counted as successful.
36. As an operator, I want status and receipts after a manager, Herdr or host restart, so that I can reconcile accepted work from local records.
37. As an operator, I want evidence before retrying a launch, so that I never rerun an input that may already have executed.
38. As an operator, I want to recover a still-actionable request under its original ID, so that takeover does not create a second decision or recreate its agent.
39. As an operator, I want cancellation and a racing response to have a recorded order, so that I can tell whether my response was accepted.
40. As an operator, I want cancellation intent, tab closure, execution settlement and capacity release displayed separately, so that I do not start conflicting work on a false signal.
41. As an operator, I want to clear an uncertain hold only after establishing that conflicting work cannot resume, so that I can proceed without rewriting the original outcome.
42. As an operator, I want to confirm sensitive actions myself, so that the managing agent can assist but cannot consent for me.
43. As an operator, I want inspection to show missing or contradictory evidence, so that uncertainty is not mistaken for a free slot or an available action.
44. As an operator, I want settlement and cleanup to preserve reports and evidence, so that I can investigate an outcome after tabs close.
45. As an operator, I want ordinary standalone Bootstrap runs to continue working as before, so that I can adopt factories without migrating existing workflows.

## Implementation Decisions

### Boundaries and operating interface

- Follow the existing agent-driven graph architecture. The managing Pi/Herdr session controls factory admission and launching and records operator decisions; it is not a node scheduler. After release, agents still claim handoffs, validate and report results, route verdicts, and drive revisions. Launch into the managing pane's Herdr workspace. Existing standalone Bootstrap commands, plans and persisted runs remain compatible and do not acquire factory slots.
- Give factories a common operation boundary for the Pi UI and structured tools. A direct `/factory` command surface should discover factories, inspect status/queue/receipts/requests/evidence, and guide the operator through lifecycle, publication, submission, response, discard, run cancellation, launch retry and clearance. Initial brief entry and responses are direct human interactions, not interpreted chat. Agent-facing tools can inspect and prepare actions; they cannot fabricate a human confirmation or submit a routing choice on an operator's behalf. Human confirmation is bound to the exact target and action, not a model-supplied flag; validate eligibility again at commit. Apply these rules to existing run controls when they mutate factory-managed work. Read-only factory inspection may not resume management, repair delivery or trigger cleanup as a side effect.
- Distinguish a stopped factory from an unmanaged one. Opening Pi never activates admission or launching. Stop prevents new admission and new launch attempts once acknowledged; it is not cancel, cleanup, discard or clearance. Do not undo a launch that already crossed its start boundary. Preserve access to existing run controls and actionable requests under exclusive management even when admission and launching are stopped. Publication does not resume a stopped factory.
- Enforce at most one managing session at a time. Resume or confirmed takeover establishes exclusive local authority and reconciles saved state before scheduling. Fence stale managers at mutation and launch/release boundaries, including when a process ID has been reused or the host rebooted. Do not steal authority on heartbeat age alone. Non-managing sessions are read-only until they obtain authority. In the initial release a person with access to the managing session may operate it; record actor information only when reliably available, without claiming verified identity.

### Publication and input admission

- Publish a complete, immutable, validated definition and move the current version pointer in one durable commit. Versions increase per factory (`v1`, `v2`, …). Validate the exact executable definition without launching: include graph shape, dependencies, contracts and checks, revision mappings and limits, and the run attempt budget floor for first attempts. Share validation with launch where practical; a successful dry run today is not, by itself, evidence that every launch invariant passed. On rejection, keep the prior current version and return actionable diagnostics. Publishing while work is queued or running does not rewrite its definition.
- Preserve target checkout, plan and node instructions, contracts, intervention rules, resolved limits, persona prompts, resolved models and thinking levels, and declared tool, skill and extension policies. Launch consumes the preserved version rather than resolving the draft, aliases, persona names or defaults again. Policies that inherit Pi's available tools or skills do so at launch; the installed extension/skill contents, Pi runtime, checkout contents and credentials are not snapshotted. Preflight validates integrity and compatibility against live prerequisites and operator ceilings; known pre-launch failures block the head without substituting a version, model or limit. Retain old versions; republishing a preserved definition creates a new one after validation. No in-place edit, deletion, revocation or pointer rewind.
- A submission consists of factory ID, stable submission reference and a nonblank plain-text brief. Preserve multiline text exactly, treating file and issue references as literal text. The brief is run input, not a way to change graph, target or permissions. Deliver it via the existing immutable Bootstrap task-input and bounded shared-brief mechanism; when the prompt excerpt is shortened, the full brief remains retrievable through the existing input reader. Initial limits: **16 KiB UTF-8 per brief** and **32 queued inputs per factory** (including a blocked or retryable head, excluding active runs and history). Show the limits, reject additions that exceed them, and never evict accepted inputs to make room.
- In one commit, allocate the input ID and FIFO position, and bind the reference, exact brief and version current at that instant. Admission racing publication follows durable order. Acknowledge only after this commit, with input ID, reference, bound version and disposition; do not wait for a run. Distinguish a definite rejection from an uncertain write. Resolve uncertainty by read-only receipt lookup or retry with the same reference. An identical retry returns the original receipt and current disposition without consuming queue capacity or rebinding, even if the input is discarded or the current version changed; a changed brief with the same reference is a conflict. To repeat intentionally, use a new reference. Discard with confirmation is allowed only before launch has begun; retain its receipt and exclude it from scheduling. To edit an unstarted brief, discard and submit a new one.

### FIFO, capacity and launch recovery

- Process inputs in recorded acceptance order with no silent bypass, including when the head has a preflight failure or awaits explicit retry. At most one launch or run occupies the factory slot and at most one occupies the checkout across all local factories. Resolve equivalent paths to the same checkout identity. Coordination for that checkout must be shared across workspaces and factory state roots. Other factories on different checkouts may proceed; no inter-factory priority guarantee. A waiting intervention, manager loss or factory stop does not free capacity. This excludes standalone launches, manual edits and shared external resources from the guarantee.
- Before invoking launch, durably record the launch attempt, both holds and its stable Bootstrap `request_id`. Make its association with the exact Bootstrap launch/run recoverable without launching, including when the acknowledgement is lost. Before any agent can act on release, commit affirmative durable evidence that execution **may start**. A missing release record, generic `interrupted` status or successful status lookup is not proof of non-release. Ensure aborted or stale launchers cannot release after an attempt is proven unable to do so. Do not use a new `bootstrap_generate` call as a status probe.
- Reconcile on explicit resume from committed evidence. Known never-started inputs can launch normally when eligible. Only an explicitly confirmed retry may start another launch attempt for an input whose previous attempt is durably proven never released and can no longer release. Preserve the old attempt and use a new `request_id` while retaining input, bound version and FIFO position. When execution may have occurred and there is no reliable settlement, retain both holds and do not relaunch. A launch that may have executed is not discardable; intentionally repeating it after clearance requires a new submission.
- Automatically release holds only on proven non-release with no remaining release authority, or reliable execution settlement with no original attempt, revision or in-flight tool still able to act on the checkout. Cleanup is not required for settlement. Persist cancellation intent separately from settlement; a cancelled disposition, closed tab, expired heartbeat or reboot alone proves neither settlement nor absence of conflicting effects. Known or suspected detached or remote work that could conflict must be stopped or isolated first. If release is uncertain, require operator clearance with confirmation, reason, supporting evidence of non-resumability and acknowledgement of unknown past effects. Record clearance and retire the input from launch eligibility without changing its historical outcome or undoing effects.
- Durability covers manager/agent and Herdr crashes, ordinary reboot and OS crash on one host with intact, non-rolled-back local storage. Acknowledge only committed writes; atomic replacement without a crash-durable commit is insufficient. Preserve definition versions, receipts (including discards), launch and hold history, request and response records, and authoritative evidence for admission, cancellation, settlement and clearance. No auto-pruning or destructive run cleanup that would remove required records. Missing, unreadable or contradictory evidence blocks affected operations without overwriting it. A storage failure must not silently lose accepted work. Capacity coordination and fencing protect against ordinary failures and races, not malicious same-user processes. Arbitrary tools' undisclosed background effects cannot be ruled out or made exactly-once.

### Intervention and routing

- Opt in by node in the definition. Only an enabled, admitted attempt initiates a request; offer a nonempty applicable subset of plan choices, including any choices the definition requires. Validate stable factory, input, run, node, attempt and request identity. Record the question, reason, evidence or references, choices and optional recommendation. Allow at most one pending request per attempt, with another possible after resolution; no unsolicited route or agent withdrawal. Protect the waiting boundary so the requesting attempt does not continue ordinary work while waiting.
- Silence is indefinite waiting, neither decline nor consent. Pause the requesting attempt's execution timeout for the human wait. No direct or transitive dependant, including a join, may time out solely due to that wait. Independent prerequisites and branches retain their own deadlines and may continue; a live wait does not suppress detection of actual agent loss. Waiting retains factory capacity and existing ownership rules.
- A human selects one of the presented choices or explicitly declines, optionally with free-text guidance. Text alone is not a response. Decline is not approval; the attempt may proceed only within its assignment and plan, otherwise report inability to proceed. Record the response once; identical retry returns the recorded outcome and conflicting retry is rejected. Serialize the response-versus-cancellation decision durably: if cancellation wins, close the request and reject a response; if a response wins, keep it without preventing later cancellation. Cancellation or failure can terminate a request. Neither a recorded response nor a wake-up can revive a cancelled or dead attempt.
- After takeover, keep a pending request actionable under its original ID only if its original attempt is verified able to continue. Wake-ups may be retried only for the same response and verified waiting attempt. Persist the claim that permits continuation before further work so duplicate wakes do not restart a turn. If consumption or execution is uncertain, surface it rather than replaying the attempt. Continue to recover ordinary Bootstrap handoffs only by redelivering the same demonstrably unclaimed handoff to a verified live destination, never by recreating a worker.
- Only intervention-enabled decision nodes may offer routing choices. Map them to the existing approval or rejection verdict; other choices only direct the node within its assignment. A chosen route binds one attempt, and clarification cannot replace it. A fresh review attempt may receive a fresh choice. If nobody was asked or the person declined, a node may supply its own verdict where its plan permits. When a route binds, Bootstrap fills the result verdict from the recorded choice and rejects a conflicting submission. Only a valid successful result can route: checks, contracts, artifact integrity and successor admission still apply. Surface conflicting guidance or an impossible route; where it cannot be resolved within the assignment, report non-success with neither route taken.
- Approval finalizes the loop and fires only declared forward edges; a sink completes its branch, not the whole run unless ordinary settlement rules are met. Rejection uses the existing feedback edge to revise the entire loop body on the same live agents in dependency order, with recorded review findings and guidance. Respect both per-loop and run attempt limits. Even with a known exhausted budget the revision choice remains selectable: warn before selection, record which limit prevented revision, apply the declared `on_exhausted` disposition, and neither open forward edges nor start a partial iteration.

### Status and operator controls

- Render a compact live factory summary and on-demand detail from authoritative records. Show managed/stopped/unmanaged state, current definition, active run, queue and outstanding attention. Surface new requests, failed runs, blocked queue heads and uncertain holds prominently in managing Pi; missed notifications do not hide outstanding items. Reuse the existing run status, report and graph views where practical.
- Show FIFO order and the blocking cause for the head: inactive factory, its own occupied slot, checkout held by another factory, bound-version/preflight problem or uncertain hold. Name the blocking factory, input or run when known; later entries can point to the head. Show bound version on receipts, queue, run status and reports, distinguishing inherited settings. Display publication errors without implying the draft replaced the current version.
- Show pending, resolved, cancelled and uncertain requests. Display response recorded, consumption, verdict and successor/revision admission as separate observations; mark stages unknown or inapplicable as appropriate. Show remaining revision capacity and the exhaustion consequence relevant to the presented choice. Show whether launch retry is eligible and why; for uncertainty, identify the hold and missing evidence. Stop, discard, cancel, close tabs and clear hold are distinct. Require explicit human confirmation of target and consequences for discard, run cancellation, takeover, launch retry and clearance; confirmation never grants authority missing from the recorded evidence.

## Testing Decisions

- **Primary seam:** exercise the command/tool operation boundary shared by Pi adapters. Use the existing Bootstrap service/run fixture with real worker behavior, simulated Herdr and isolated local storage. Assert receipts, queue order, command eligibility, admitted attempts, checkout exclusion, observed outcomes and reports, not private helpers or storage layout. Extend the fixture only where needed for additional operators, interruption and time control. Existing graph loop, joins, handoff recovery, cancellation and status/report tests are prior art.
- **Admission and scheduling:** publish and race publication against acceptance; verify first-commit binding, lost acknowledgement, identical and conflicting retries, limit enforcement, discard versus start, stop versus start, old-version compatibility blocks, FIFO and cross-factory exclusion across aliased paths and separate state roots. Test that known-unreleased retry keeps the input and version but creates a new launch attempt; a possibly executed input cannot retry, including after clearance. Confirm human waiting retains the slot and known settlement frees it even with tabs still open.
- **Intervention:** exercise disabled and enabled nodes, a pending request during independent progress, transitive dependants and joins, decline and choice, repeated wake-up/response, response versus cancellation in both orders, response recorded without consumption, consumption without verdict, and valid verdict without successor admission. Cover conflicting verdicts or guidance, failed contracts/checks, successful sink approval with other work outstanding, normal same-agent revision and each exhausted budget. Test the displayed states and actions, not notification count or terminal layout.
- **Process/runtime seam:** reuse the isolated Bootstrap runtime harness and supervised child processes for loss of manager/agent, competing managers, stale authority and crashes around publication, acceptance, hold acquisition, release permission, launch acknowledgement, response/consumption and settlement/clearance. Cover a crash before release authority exists and after an agent can act, including lost or damaged evidence. Verify that process loss is not treated as evidence of non-release or absence of side effects. Use real local storage at this seam; process-kill tests do not by themselves prove power-loss durability. Verify the commit boundary against OS/filesystem durability semantics and exercise it with controlled durability fault injection where supported.
- **Pi/Herdr smoke:** verify manual multiline submission, discovery of an intervention, human confirmation that cannot be supplied by an agent tool, and drill-down from queue to run/recovery status. Retain an end-to-end example that revises, approves, settles and starts the next input, plus a takeover case showing an actionable request or a blocked uncertain hold without replay. Use the existing opt-in live test harness without personal state or production credentials. Run standalone Bootstrap regressions; missing runtime capabilities are unverified, not passing release coverage.

## Out of Scope

- Automated triggers, web wrapper, externally routed notifications, multi-user access control or a daemon that accepts inputs when Pi is unavailable.
- A general-purpose workflow platform, central node scheduler, dynamic graph changes, arbitrary graph jumps or unbounded revision.
- Concurrent runs within a factory or against the same checkout, automatic worktrees, sandboxing and generalized locking of external resources.
- Cross-host takeover, backup restoration guarantees, disk-loss recovery, automatic corruption repair, guaranteed execution survival and exactly-once tool effects.
- Automatic replay of uncertain work, deletion or revocation of published versions, destructive pruning of required evidence, and migration of existing standalone runs into factories.

- An operating guide should walk through first use, a blocked head, an intervention, takeover and clearance. Call out that manual and standalone work is not coordinated, and that cleanup is not evidence that external effects stopped.

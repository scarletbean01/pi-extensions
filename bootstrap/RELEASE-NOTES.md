# Graph topology, bounded review loops, and risk-lane gating release

Bootstrap supports dependency graphs (`topology: "graph"`), bounded review loops (`decision`), `bootstrap.json` graph limits and path-based risk lanes (`lanes`), automatic cleanup on success (`cleanup: "on_success"`), and the live `/bootgraph` widget. Agents still coordinate directly through durable files with no central scheduler. See [Graphs, review loops, limits and automatic cleanup](README.md#graphs-review-loops-limits-and-automatic-cleanup) and [Upgrade, rollback and operator playbook](README.md#upgrade-rollback-and-operator-playbook).

## What is new

- **Graphs, fan-out and joins (`topology: "graph"`):** Node-form plans (`persona` / `node_id`) can declare `depends_on` edges (up to 32 nodes; circular `depends_on` dependencies and legacy `name` entries are rejected). Fan-out nodes track delivery per edge (`edge_deliveries`), so delivery repair re-sends only missing edges. **Joins** (nodes with multiple dependencies) support `join_policy` (`all_success` default, or `allow_partial`) and start once under one exclusive join claim (`<dest>.handoff.json`). `bootstrap_status` shows derived edge states (`pending`, `fired`, `dead`) and which join inputs are pending or dead.
- **Review loops (`decision`):** Nodes in node-form `chain` and `graph` plans can route by a required two-value string enum in `output_contract` (`approve` moves forward; `reject` sends feedback back to `on_reject`). On rejection, the **loop body** runs again in order as a new **attempt** on the same live agents, bounded by `max_revisions` (1–10, default `3`) and `max_total_attempts`. Only `status: "success"` decisions route; a `partial` or `failure` decision, or a body failure, stops the loop right away. `bootstrap.json` adds an optional `graph` block with `defaults` and `ceilings` (`maxRevisions` and `maxTotalAttempts`), merged field by field with the lower ceiling winning.
- **Parked-agent safety:** Loop-body agents stay alive and idle (**parked**) between attempts with task tools disabled and stall diagnosis turned off. Closing a parked or finalized agent's tab records no failure. If a parked agent exits when a revision is needed, the feedback edge becomes `dead` and the decision node ends as `needs_attention` without replaying work.
- **Ownership, checks, cancellation and timeouts in loops:** Loop-body nodes keep `write_paths` ownership until **finalization** (`<instance>.finalize.json`, raced exclusively against revision claims); dry runs warn when a whole loop shares paths with another writer, and ownership deadlock combinations involving loops are rejected during planning. `required_checks` are verified per attempt and per edge. `task_timeout_ms` applies per attempt; graph and join dependency waits (`dependency_wait_timeout_ms`) track latest useful upstream progress. `bootstrap_cancel` and `fail_fast` propagate through graphs and loop bodies, including parked agents.
- **Automatic cleanup (`cleanup: "on_success"`):** Defaults to `on_success` for `graph` and `manual` for `chain` and `team` (`cleanup_settle_ms` default `3000`ms). When a run finishes as `succeeded` with every loop finalized and every delivery settled, owned tabs close automatically while session files and reports stay intact. A background watcher handles this and sends a follow-up message; `bootstrap_status`, `/boot` and `/bootgraph` also finish cleanup lazily if the original dispatcher closed. Non-success runs keep their tabs open.
- **Widget and reports for graphs and loops:** Interactive dispatcher sessions show a live box-drawing graph widget (dry runs show the same layout without status colours), controlled with `/bootgraph <task_id>` and `/bootgraph clear`. `bootstrap_status` shows attempt counts (`attempt N/M`), `parked`/`finalized`, `last_verdict`, edge states, and join inbound status; `bootstrap_report` lists every attempt, verdict history, and blocked-join causes.
- **Graph-aware cancel, recover and report:** `bootstrap_cancel` cancels downstream dependents and loop bodies, and settles pending/failed outbound deliveries to cancelled unclaimed successors (including from approved decision nodes and live loop nodes blocked while sending — the run settles because its cancellation means the handoff can never be delivered) in both `on_success` and `manual` runs while keeping saved results intact; `bootstrap_recover` inspects every edge and attempt (`source` selects a specific join input for `retry_delivery`) and skips finalized or unapproved decision edges; `bootstrap_report` keeps mixed failure and cancellation causes on blocked joins alongside loop histories and reports never-sent undelivered edges settled by cancellation.
- **Learned constraints at launch (`.pi/constraints.json`):** Projects may define validated learned constraints (`id`, `text`, `provenance`, `status: "active" | "retired"`) in `<project>/.pi/constraints.json`. Factory launches (and standalone runs opting in with `use_learned_constraints: true`) read the file once at launch, inject active entries into the shared brief's `Constraints:` section for the whole run without changing published definition versions, fail closed on invalid/unreadable files or brief overflow, and freeze the canonical file `digest` and `used_ids` into the version 9 manifest (surfaced in `bootstrap_status`, `bootstrap_report`, and `/factory inspect`). Missing `.pi/constraints.json` leaves behavior, versions, and fingerprints unchanged.
- **Constraint proposals, human confirmation, and retirement (factory SQLite schema v12):** `factory_propose_constraint` lets managers propose adding or retiring learned constraints only after finished runs with a revision or human-responded direction intervention (verifying `evidence_ref` against real run evidence and persisting verified eligibility across cleanup); deterministic normalization (`NFC`, collapsed whitespace, lowercased) drops duplicates (`dropped_duplicate`), named `conflicting_ids` are displayed alongside the full active list, and only interactive `/factory review-proposal`, `/factory retire-constraint`, and `/factory resolve-conflict` confirm, reject, retire (recording `retirement` provenance), re-confirm, or abandon constraints using binding/ETag checks and durable two-phase `pending_write` -> `synced` writes (mode-preserving `fsync` + pre-rename digest check + `rename` + dir `fsync`). Older SQLite schema readers reject v12 (`factory_constraint_proposals`), while factories without proposals keep identical run/manifest behavior and read-only inspection never migrates v11 databases. Note that `.pi/constraints.json` remains `version: 1`, so an older Ticket 18 reader binary will fail closed on any constraints file containing a `retirement` provenance key (blocking its launches until read by Ticket 19+).

## Persisted-state versions and compatibility

- Graph runs with `decision` nodes use **version 6** (`GRAPH_REVIEW_VERSION = 6`) for manifests, agent configurations (with `topology: "graph"`), and result records (`review_plan`, without a `topology` field on results). The previous shipped release's reader supports only versions 1–2 (`READABLE_VERSIONS = [1, 2]`), so rolling back rejects every v3–v6 run (all `graph` runs and all `chain` runs with `decision` nodes).
- Versions by plan shape:
  - **Version 1**: legacy persona-keyed runs (still read, reported and cleaned up without rewriting).
  - **Version 2**: `chain` and `team` runs without `decision` nodes — requests, manifests, configs, results and fingerprints stay byte-identical when new options (`cleanup`, `cleanup_settle_ms`) are omitted; also used for **result files** of loop-free `graph` runs (including joins).
  - **Version 3**: manifests and agent configurations for `graph` runs without joins and without `decision` nodes (result files stay version 2).
  - **Version 4**: manifests and agent configurations for `graph` runs with joins and without `decision` nodes (result files stay version 2).
  - **Version 5**: manifests, agent configurations and result files for `chain` runs with `decision` nodes.
  - **Version 6**: manifests, agent configurations and result files for `graph` runs with `decision` nodes.
  - **Version 7**: runs containing `kind: "command"` nodes (`COMMAND_VERSION = 7`).
  - **Version 8**: runs with active project `.pi/bootstrap.json` `"lanes"` configuration (`LANE_VERSION = 8`) and `<reviewer>.<attempt>.lane-before.json` / `<reviewer>.<attempt>.lane-after.json` snapshots.
  - **Version 9**: runs launched with a `.pi/constraints.json` snapshot (`CONSTRAINTS_VERSION = 9`, carrying `learned_constraints` verified by canonical digest and `used_ids`). Older readers reject version 9 rather than misreading it.
- New sidecar records (`cleanup-policy.json`, `<instance>.finalize.json`, `<instance>.<n>.transition.json`, `<reviewer>.<n>.revision.json`, join/per-edge handoffs) carry version 1 schemas and fail closed on unsupported versions.
- **Do not mix releases within a run**, including running `/reload` after updating extension code under live agents. Upgrade between runs.

## Known limitations

- **Dry run does not check the `max_total_attempts` floor:** `bootstrap_generate` with `dry_run: true` accepts a `max_total_attempts` below the planned node count (whether passed directly or from `bootstrap.json` `graph.defaults.maxTotalAttempts`) that a real launch rejects (`"max_total_attempts must cover the first attempt of every planned node"`).
- **Manual cleanup of an unfinalized dead-reviewer `needs_attention` run:** Calling manual `bootstrap_cleanup` on an unfinalized run whose decision agent died after rejecting writes a generic finalization without the exhaustion cause, turning the node into `failed` and losing the dead-agent cause (in a `graph`, calling `bootstrap_status` first finalizes it as `needs_attention`; in a `chain`, or if `bootstrap_cleanup` runs first, it becomes `failed`).
- **`retry_delivery` on a doomed join before disposition:** Calling `bootstrap_recover` (`retry_delivery`) on a join where a non-loop sibling already failed, before the join writes its `blocked` disposition, still re-sends an unclaimed sibling handoff once.
- **Held ownership after uncertain restart or unconfirmed command termination:** An agent with unknown effects (accepted a handoff before restarting, leaving a `needs_attention` disposition) keeps its `write_paths` ownership held (`held_uncertain`) until an operator intervenes; `bootstrap_cancel` does not release it. For `kind: "command"` nodes, an unconfirmed process-group kill on timeout, normal exit (even exit 0 with a valid contract), or cancellation likewise fails closed as `needs_attention` (without triggering `fail_fast` on timeout/exit unconfirmed termination), records full `command_evidence` with `termination_error`, and keeps `write_paths` ownership held until `bootstrap_cleanup` kills and verifies the `.pgid.json` group dead for direct runs. For factory-managed runs, `bootstrap_cleanup` is refused and neither clearing a hold (`/factory clear`) nor `bootstrap_recover` kills or verifies the process group — the operator must kill the named process group by hand and verify it has exited before clearing the hold. **Command process-group boundary:** termination is verified only for the command's original process group; a descendant that calls `setsid` or daemonizes leaves the group and cannot be tracked or verified without an OS boundary (cgroup/container).
- **Run-wide loop check for blocked-join propagation:** In a `graph` run, automatic settling of blocked downstream nodes (including turning a dependency-wait timeout `needs_attention` into `blocked`) checks whether the run has any `decision` node anywhere rather than per branch, so adding a review loop in one branch changes how a blocked loop-free branch ends (`blocked`/`failed` instead of `needs_attention`).
- **Risk-lane snapshot forge boundary (Ticket 16 frozen):** Missing, corrupt, truncated, or digest-mismatched lane snapshots fail closed (`closed` when `lanes.closed` is configured, else `wide`), and the reviewer refuses an existing `<reviewer>.<n>.lane-after.json` that does not match its live working-tree snapshot (even if it matches a forged baseline); however, while Ticket 16 workspace/OS isolation is frozen and session files live under agent reach in `.pi/agent-sessions/<task>/`, a loop-body agent could still forge `<reviewer>.1.lane-before.json` with a recomputed `snapshot_sha256` matching the modified working tree, pre-plant `<reviewer>.<n>.lane-after.json` equal to the live tree, or tamper with `<reviewer>.<n>.lane-after.json` after the worker writes it, and yield `contained`.
- **Learned-constraints pre-launch trust boundary (Ticket 16):** Mid-run edits to `.pi/constraints.json` cannot affect an in-flight, recovered, or taken-over run because its launch-time snapshot and canonical digest are frozen in the version 9 manifest and verified on read; however, because `.pi/constraints.json` lives inside the project checkout and Ticket 16 write-scope isolation is frozen, file contents written before a new launch affect that launch (and same-user processes with write access to `.pi/agent-sessions/<task>/` could rewrite both `manifest.json` and its `learned_constraints.digest`).
- **Inherited core boundaries:** Atomic writes are not fsynced; ownership is advisory in `shared_cwd`; claimed attempts without results are never replayed automatically; hooks cannot interrupt an in-flight tool call; synthesis, collaboration leases (and parking outside loops), supervision, lazy launch, concurrency slots, archive service and isolated worktrees remain unavailable; runtime requires POSIX `/bin/sh`, Node 26+, installed Pi and compatible Coms/Herdr.

# Model aliases, persona discovery and allowed skills

See the [migration guide](MIGRATION.md) before launching personas carried over from other tools or personas that use old aliases.

- Bootstrap discovers personas in `<project>/.pi/agents` and the global `agents` folder in Pi's agent directory (`~/.pi/agent/agents`, or `$PI_CODING_AGENT_DIR/agents` when that variable is set). The project wins on case-insensitive name collisions. Project team definitions stay in `.pi/agents/teams.yaml`. The interactive `system-select` extension, `/system` command, `--agent` flag and persona-cycling shortcuts are removed.
- Define aliases in global `~/.pi/agent/bootstrap.json` (or `$PI_CODING_AGENT_DIR/bootstrap.json`) and optionally in `<project>/.pi/bootstrap.json`. The shape is `{"modelAliases":{"review":{"model":"openai/gpt-5","thinking":"high"}}}`. Each alias has a full model ID and an optional thinking level. Alias names are case-insensitive, duplicate names within a file are invalid, and a project entry replaces the entire global entry. Missing files contribute no aliases. Bootstrap ships zero aliases. Invalid config stops planning with the file and key.
- A persona can use an alias or full model ID. The `model:` suffix takes precedence over the persona's `thinking:` field, which takes precedence over the alias's `thinking`. An invalid level or unknown alias stops planning. An omitted model inherits the launching session's model, and planning fails if there is no model to inherit. The dry run shows the resolved model and thinking level.
- A missing `skills:` field keeps every skill Pi discovers, an empty field keeps zero, and a comma-separated list keeps the named skills with exact, case-sensitive matching. The dry run previews the list. Unknown names fail agent startup before work is released, and diagnostics name the persona and the unknown skills. Allowed skills save prompt context. They provide no permission boundary.
- Agents prepend the persona text to Pi's default prompt and omit Pi's built-in harness-documentation block when it matches the installed prompt shape. Agents can still read the installed documentation by path. Extension-contributed prompt rules and tool guidelines stay in the prompt.

## Known limitations

- Trimming extension-contributed rules and configuring the full extension list per persona are deferred. Personas can still name extra extensions with `extensions:`.

# Hardened team/chain core release (historical)

That earlier core milestone shipped tickets 01–09 plus release gate 13 (in that milestone, optional tickets 10–12 and 14–24 were not yet shipped; graph topology and bounded review loops shipped in the release above). See [migration and recovery guidance](README.md#upgrade-rollback-and-operator-playbook).

Shipped capabilities:

- Repeated personas with distinct node, attempt and agent identities; v2 manifests/configs/results and safe v1 inspection, reporting and cleanup.
- Bounded run briefs, peer rosters, output contracts, artifact digests/provenance and on-demand upstream input reads.
- Explicit execution outcomes and dependency policies, original cause chains, mixed-outcome reports and verification evidence whose applicability changes after relevant edits.
- Durable handoff offers and exclusive destination claims before execution, duplicate notification suppression, rejection diagnostics and serialized delivery repair from saved results.
- Cancellation, configurable execution/dependency/liveness deadlines, grace-bounded force close and session replacement without inherited task authority.
- Independent teams, optional fail-fast behavior, declared shared-directory ownership and serialization of known conflicting writers; no automatic worktrees.
- Request idempotency, cross-process locks, interrupted launch reconciliation and cleanup by stable owned resource identity.
- Existing generate/status/report/cleanup surfaces, required recover/cancel operations and basic `/boot` inspection. Unsupported workspace strategies and topologies fail closed.

Known limitations:

- Atomic file publication is not fsynced; power loss may lose recent updates. Ownership is advisory, not a filesystem sandbox or protection from same-user processes.
- A claimed attempt with no result needs an explicit effects review. There is no automatic side-effect replay or exactly-once side-effect guarantee.
- Handoff repair requires a live waiting successor and dispatcher Coms. The default dependency wait window is 5 minutes; retries have a 30-second delivery wait and a five-attempt budget.
- Hooks cannot interrupt in-flight tools. Force-closing a pane does not prove external side effects stopped. Cancellation queued behind a run lock waits until the lock is acquired (up to 15 minutes).
- Read scopes do not lock writers. Check evidence can become stale after a agent's successful result; that historical result is retained. Declare relevant scopes and recheck when needed.
- All agents are eagerly launched in the existing project directory. In that earlier core milestone, synthesis, collaboration leases, supervision, lazy launch, concurrency slots, archive service, and isolated worktrees were unavailable (graph topology and bounded review loops shipped in the release above).
- Runtime requires POSIX `/bin/sh`, Node 26+, installed Pi and compatible Coms/Herdr. Windows launching is unsupported. Do not mix releases within a run.

Release validation uses the isolated deterministic and runtime suites (`node bootstrap/run-tests.ts all`), including combined core acceptance scenarios. Runtime uses installed Pi and Coms with a scripted local fake provider. Real-provider execution and live Herdr tab lifecycle are not verified by these suites. Live Herdr coverage remains explicitly opt-in; consult the release report for exact counts and skips.

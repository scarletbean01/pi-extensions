# Factory queue, stop, and discard

`/factory stop <factory-id>` is an interactive, directly confirmed control. Its durable record fences new brief admission and FIFO launch reservation. The acknowledgement does not cancel a run or undo a launch that already committed its reservation boundary. Queued receipts, active runs, holds, requests, and run controls remain available. `/factory inspect <factory-id>` reports `stopped: true` and a `stopped` head status, with the underlying eligibility and blocker in `without_control_fence`. Inspection does not change state.

`/factory resume <factory-id>` explicitly establishes management and clears the stop in a single transaction. Opening or inspecting a factory does not resume it, and publishing a version does not clear the stop.

The managing Pi session shows a live footer with management state, versions, queue depth, active run, and outstanding attention. It alerts on blocked heads, failed runs, uncertain evidence, and automatic scheduling errors. Use `/factory inspect <factory-id>` for durable blocker, hold, and attempt evidence; `/factory receipt <factory-id> <reference>` for the receipt; and `/bootgraph <task-id>` for the run. The watcher settles only runs with verified settlement, even if their tabs are still open, and automatically advances the eligible FIFO head after resume, settlement, or clearance.

`/factory discard <factory-id> <input-id>` is available only in an interactive managing session. Pi confirms the exact input, reference, current waiting position (not its permanent acceptance ordinal), bound version, and consequences. Declining leaves the receipt unchanged. The operation revalidates current manager authority, the receipt and its queued disposition under a write transaction after confirmation. The launch reservation uses the same durable database write boundary, so whichever commits first determines eligibility. A discarded receipt remains queryable and an identical submission retry returns that historical receipt; it cannot make the input eligible again. Use a new submission reference for intentional repetition.

The persistent record is local factory storage with SQLite `synchronous=EXTRA`. Missing or damaged control evidence blocks admission, launch, and resume rather than silently clearing a possible stop. Inspection reports `control_error`, and identical submission retries can still retrieve intact receipts. An existing management-era database without the controls table cannot be safely distinguished from one that lost its stop evidence; it requires recovery of the control evidence, not automatic initialization. Existing run cancellation, settlement, request response, and clearance operations remain available while stopped.

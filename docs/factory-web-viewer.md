# Factory Web Viewer

A standalone, read-only local dashboard for observing factory records without Pi, Herdr, or a managing factory session. It binds only to loopback and never invokes launch, recovery, repair, reconciliation, settlement, or cleanup operations.

## Start and stop

Use Node 26+ from the extension checkout:

```sh
node factory/viewer/cli.ts
```

Or point to a specific factory state database:

```sh
FACTORY_STATE_PATH=/absolute/path/to/factories.sqlite node factory/viewer/cli.ts
```

When `FACTORY_STATE_PATH` is omitted, the viewer uses `factories.sqlite` in `PI_FACTORY_STATE_DIR` (or `PI_BOOTSTRAP_STATE_DIR`, defaulting to `~/.pi/agent/bootstrap-sessions`), matching `/factory list`. An empty `FACTORY_STATE_PATH=""` is rejected, whereas an empty `PI_FACTORY_STATE_DIR=""` matches `/factory list`'s default-path rules and resolves `./factories.sqlite` relative to the working directory. `FACTORY_VIEWER_HOST=127.0.0.1|::1` chooses the loopback address (default `127.0.0.1`) and `FACTORY_VIEWER_PORT=PORT` chooses a port (otherwise an ephemeral port is selected). Ctrl-C stops only the viewer. Keep the URL local and do not proxy it to another host.

## Views

The sidebar lists published factories (persistent on desktop, and a keyboard-accessible drawer on narrow screens). Choose a factory to open Live Graph, or use the view navigation (and URL query parameters `?factory=...&view=...`) for Factories, Live Graph, Inspect, Queue, Receipts, Requests, and Proposals. The browser displays only snapshot evidence: unknown, partial, or unavailable fields are labelled (`no records`, `not applicable`, `evidence unavailable`) rather than guessed. Receipts are not run reports; proposals are not the active constraints file. The viewer offers no factory action controls.

Verified run topology is displayed when provided by the API; missing topology is not inferred. The node diagram supports pointer drag, wheel zoom, and keyboard pan/zoom (`+`/`-`/`0`/arrow keys and toolbar buttons); keyboard-focusable node selection (`Enter`/`Space` or click) displays available status/reason, current attempt details, and a bound-version configuration link when the snapshot supplies a bound version. Periodic 2-second polling and client-side Stale overlay are left for the live-refresh follow-up ticket; switching factories or views aborts in-flight requests and discards mismatched responses.

## Local asset/API contract

The browser requests only these local asset routes:

- `GET /` or `/index.html` — HTML shell (skip link, landmarks, single `h1`, drawer button, seven-view navigation)
- `GET /vendor/materialize/materialize.min.css` — vendored upstream `materialize-css@1.0.0` (MIT) CSS with remote URL comments stripped and no Materialize JS, Material Icons font, or Roboto/Google Fonts
- `GET /style.css` — local responsive overrides and system font stack
- `GET /app.js` — local vanilla JS client (no `innerHTML`/`eval`, safe DOM APIs only, custom accessible drawer and `<details>` accordions)

No CDN, external fonts, icon service, or runtime remote asset is used. All static routes are exact-match entries in the server allowlist with `x-content-type-options: nosniff`, `cache-control: no-store`, and strict `content-security-policy`. Snapshot routes consumed by the client are `GET /api/factories`, `/api/factories/:id/live`, `/inspect`, `/queue?filter=open|all`, `/receipts?reference=...`, `/requests`, and `/proposals`.

Live Graph (`GET /api/factories/:id/live`) verifies the selected factory's binding, capacity holds, and release evidence without calling generic standalone run status or widget paths (the reader passes only passive preflight and raw non-release evidence verifiers, never `status`, `statusWithCleanup`, or `settlementObservations`). Every snapshot carries `factory_id`, `current_version`, `checked_at`, `run` (`{ run_id, attempt_id, bound_version }` or `null`), `state` from the closed set (`"running" | "ended" | "idle" | "waiting" | "blocked" | "uncertain"`), and `reason`; failing store or coordination reads return HTTP `503` (`{ error: "Evidence unavailable" }`) or `404` for an unknown factory, never a fabricated snapshot. A verified released run returns `state` (`"running"` when incomplete/needs attention, or `"ended"` once all nodes have terminal outcomes—never `"running"` after ending), `current_version` separately from `run`, distinct `outcome`, `settlement` (`"unsettled"` while active/unsettled), and `capacity_release` (`"held"`), plus `graph` (`evidence: "available"`, `bound_version`, `topology`, `nodes`, `edges`, `joins`, `feedback_edges`) drawn strictly from the run's bound definition version. Dependency edges carry `kind: "dependency"`, `dependency_policy`, and derived `state` (`"pending" | "fired" | "dead"`); joins appear on `node.join` and in `graph.joins` (with `source_links`); feedback edges appear in `graph.edges` (`kind: "feedback"`) and `graph.feedback_edges` (with `target_link`). Each node carries `status`, human-readable `status_text` (e.g. `"Waiting"`, `"Waiting (parked)"`, `"Blocked"`, `"Uncertain"`), `reason` where evidence gives one, `current_attempt` details (excluding prompts, briefs, logs, and filesystem paths), `configuration_url`, and version-bound `configuration_link` (`nodeLink` in the bound version). Settled or operator-cleared historical runs (when no active unreleased launch holds capacity) return `state: "ended"`, `run` metadata, distinct `outcome`, `settlement` (`"settled"` for settled; `"unknown"`/`"unsettled"` for cleared), `capacity_release: "released"`, and `graph: { evidence: "not applicable", absence: "not applicable", explanation }`. Every `ended` snapshot (held, settled, and cleared runs) also carries `head_status` (from `headSummary`, explaining queue head eligibility and any later `blocking_kind` blockers such as `empty`, `unmanaged`, `stopped`, `preflight`, `compatibility`, `ceiling`, `factory_held`, `checkout_held`, plus `without_control_fence`); when a queued head is waiting but blocked (`!eligible` with a non-`empty` `blocking_kind`), the `ended` snapshot preserves `state: "ended"` and its outcome/settlement/capacity facts while also attaching `launch_blocker` (`{ kind, explanation }`) and appending the blocker explanation (and any underlying `without_control_fence` blocker explanation) to `reason`. When no released run is mounted (idle, waiting, or blocked), the snapshot returns `run: null`, `head_status`, and `graph: { evidence: "not applicable", absence, explanation }` (unmanaged factories and unreleased launches use `absence: "not applicable"`, while managed factories with no attempt use `absence: "no records"`); unreleased `reserved` (and `failed_before_release`) launches deliberately report `state: "blocked"` rather than `"waiting"` or `"running"` because capacity is already reserved/held without release authorization. Missing, damaged, or contradictory release, binding, topology, control, settlement, or capacity evidence (including a damaged bound version while `current_version` is intact, a `settled`/`cleared` attempt without `release_authorized`, or a held `factory_slot` with no current attempt unless `head_status` explains it as `factory_held`) returns `state: "uncertain"`, `run: null`, and `graph: { evidence: "unavailable", absence: "evidence unavailable", explanation }` without falling back to `current_version`. Live rendering in the legacy client still accepts either top-level run fields or a nested `run`, `live_run`, plus nodes (`id` or `node_id`), edges (`from`/`source`, `to`/`target`), and `feedback_edges`.

In review loops, if a node's progress file still reflects an earlier attempt that never recorded `"completed"` (for example, the worker died before its 5-second heartbeat after finishing attempt N while attempt N+1 was already reserved), Live Graph shows that node as `Uncertain` rather than `Blocked`: this is fail-closed by design so stale progress from an incomplete prior attempt is never silently treated as healthy for the new attempt.

Viewer-owned JSON reads use `O_NONBLOCK | O_NOFOLLOW` with `fstat` regular-file verification, and handoff paths are pre-checked with `O_NONBLOCK | O_NOFOLLOW` and `fstat` before invoking shared `describeHandoff` readers (pre-checking both edge claim and join claim source-attempt result paths whenever present so an invalid edge claim cannot bypass regular-file verification on `describeHandoff`'s join-claim fallback). Viewer-owned direction and exhaustion observation readers (`directionObservation`, `directionRouting`, `directionExhaustions`) likewise verify session directories and files with `O_NONBLOCK | O_NOFOLLOW` and `fstat` without calling `BootstrapService.status` or `SessionStore.load`. A residual time-of-check/time-of-use gap remains between that pre-check and `describeHandoff`'s path-based read in `bootstrap/handoff.ts`: if a regular handoff file were swapped for a FIFO in that window, reading it could still block, though exploiting this requires local write access to the session directory and is outside the viewer's threat model.

Inspect (`GET /api/factories/:id/inspect`, accepting optional identifier-only `version`, `node`, and `factory` query parameters without duplicate keys; non-safe-integer or malformed `version` values return HTTP 400) returns `attention_summary` (covering `name`, `management`, `stop_state`, `current_version`, `capacity`, `queue_head`, and `attention` with operator explanations), `versions` (with `restored_from` provenance and `evidence`/`absence`), `damaged_records`, `runtime_assumptions` / `not_frozen`, `definition.nodes` (labelled configuration fields for `agent` and `command` nodes, policies, dependencies, joins, decisions, feedback targets, `required_checks`, and `limits`), and `operation_evidence` (summarising `attempts`, `admission`, `bound_versions`, `capacity`, `requests`, `proposals`, and `attention` with `detail_view`/`detail_url` references). Selecting a retained `version` updates `inspected_version`, `versions[*].inspected`, and `definition` to that version while keeping `current_version`, `current_definition`, `attention_summary`, `capacity`, `queue_head`, `attention`, and `operation_evidence` current; when the requested version is damaged or not retained, `definition` reports `evidence: "unavailable"` and `absence: "evidence unavailable"` without falling back to the current version. Verified node references in `dependencies.items`, `join.sources`, `policies.join.sources`, `decision` (`feedback_target_link`, `loop_body_links`), `feedback_target`, and `relationships` emit version-bound link objects (`factory_id`, `version`, `node_id`, `anchor`, `href`, `snapshot_url`), while unverified targets emit `{ absence: "evidence unavailable", explanation }` non-links; `decision.feedback_target` is a node-ID string when verified and an `{ absence: "evidence unavailable", explanation }` object when not. Passing `node` (and optionally `factory`) resolves `target_node` in the inspected version (`verified: true` with `node`, or `verified: false` with `absence: "evidence unavailable"` and an explanation when the node is unknown, the version is damaged or not retained, or `factory` does not match—never another version's configuration and never a redirect); passing matching `factory` without `node` returns `target_node` with `verified: true` and no `node`. Empty or unavailable Inspect fields use machine-readable `absence` values (`"no records"`, `"not applicable"`, `"evidence unavailable"`) with operator explanations rather than bare defaults, with these explicit exceptions: `queue_head` (from `headSummary`) omits top-level `input_id`, `reference`, and `bound_version` when `undefined` while `queue_head.input` carries the typed `absence`, `definition.limits.max_total_attempts_source` defaults to `"built-in"` when unset, and `definition.restored_from` falls back to `"not applicable"` when the inspected version is absent from `versions`.

Queue (`GET /api/factories/:id/queue`, accepting optional identifier-only `filter` = `"open"` [default] or `"all"` without duplicate or extra parameters; invalid filters return HTTP 400) lists FIFO inputs in acceptance order (`queue_position` ascending) alongside `total_count`, `evidence` (`"available" | "uncertain" | "unavailable"`), `explanation`, and `head_status` (from `headSummary`, explaining the first waiting input's `blocking_kind` with fixed operator explanations rather than raw reason text, and using a fixed disposition-specific explanation rather than run-slot-held wording when the head's disposition is non-`queued` with no active capacity hold). Each row projects `input_id`, `reference`, `queue_position`, `bound_version` (plus `bound_version_evidence: "unavailable"` if that retained version is damaged), `disposition`, `disposition_explanation`, `uncertain`, `accepted_at`, `is_head`, and version-safe identifier-only receipt links (`receipt_url` and `receipt_snapshot_url`) without briefs, prompts, or filesystem paths. The `open` filter keeps unfinished dispositions (`queued`, `blocked`, `retryable`, `launching`, `running`) and any uncertain entry (attempt-level uncertainty from `deriveRunOutcome === "uncertain"`—such as `uncertainty` entries, unreadable evidence, or unknown execution settlement on a settled or cleared run—as well as unknown attempt state, `settled`/`cleared` without `release_authorized`, or missing settlement/clearance records, plus damaged bound version on any row and missing attempt on a `settled`/`cleared` disposition), while `all` also returns cleanly finished (`settled`, `discarded`, `cleared`) entries. Keeping finished rows whose bound version is damaged and `settled`/`cleared` rows whose attempt is missing in `open` is a deliberate difference from `/factory queue --open` (which filters only on unfinished disposition, `attempt.uncertainty`, and `run_outcome === "uncertain"`), erring toward surfacing uncertain evidence. Empty queues distinguish `absence: "not applicable"` (unmanaged factory) from `absence: "no records"` (managed factory with no admitted or no open inputs); damaged, hot-journal, WAL, or unreadable factory or coordination stores return `{ factory_id, evidence: "unavailable", entries: [], absence: "evidence unavailable", explanation }` without recovery, and unknown factories return HTTP 404.

Receipts (`GET /api/factories/:id/receipts?reference=...`, requiring a single valid identifier-only `reference` within 256 UTF-8 bytes and no whitespace or control characters; missing, malformed, over-long, duplicate, or extra parameters return HTTP 400) returns `{ type: "receipt", is_run_report: false, note: "Receipt evidence is not a run report.", factory_id, input_id, reference, queue_position, accepted_at, bound_version, current_version, disposition, disposition_explanation, attempt }`. Receipts resolve strictly within the requested `factory_id` (unknown or cross-factory references return HTTP 404 `{ error: "Unknown submission reference" }`, never an empty receipt) and work read-only with no managing session; when `factory_pointers` or the current definition cannot be verified, `current_version` reports `{ absence: "evidence unavailable", explanation }` rather than falling back to `bound_version`. Recorded launch `attempt` projects only safe launch details (`attempt_id`, `state`, `state_explanation`, `bound_version`, `task_id`, `request_id`, `release_authorized`, `release_authorized_at` or `{ absence: "not applicable", explanation }`, `created_at`, `updated_at`, and `uncertain: true` when state or release authorization is inconsistent, when `deriveRunOutcome` is `"uncertain"` including unknown settlement on settled/cleared runs, unreadable evidence, or `uncertainty` entries, or when a `settled`/`cleared` attempt lacks a readable settlement/clearance record) without briefs, raw errors, filesystem paths, or run-report node counts; absent attempts distinguish `not applicable` (`discarded`), `no records` (`queued`, `blocked`, `retryable`), and `evidence unavailable` (missing attempt for launched or finished dispositions). Damaged, hot-journal, WAL, or unreadable factory stores return HTTP 503 `{ error: "Evidence unavailable" }`.

Requests (`GET /api/factories/:id/requests`, rejecting any query parameter with HTTP 400 and unknown factories with HTTP 404—guarded directly by the viewer because `/factory requests` on an unknown id currently throws at `factory/operations.ts` ~4342 due to `missing` being used before its declaration at ~6665) projects both `direction` and `exhaustion` requests (`factory_id`, `evidence`, `records`, optional `absence`, `explanation`). Each record carries `request_id`, `kind`, `node_id`, `node_attempt_id`, `state` (`"pending" | "responded" | "cancelled" | "failed" | "closed" | "unknown"`), bounded/path-scrubbed `question` (or `{ absence: "evidence unavailable" }` when damaged), `choices` (`{ choice_id, label, route? }`), `response_recorded` (`boolean` or `{ absence: "evidence unavailable" }`), separate `consumption` and `response_consumed` (`true` for `"consumed"`, `false` for `"awaiting_consumption"`/`"never_consumed"`, `{ absence: "not applicable" }` for `"not_applicable"`, `{ absence: "evidence unavailable" }` for `"unknown"`), `reconciliation` (`"pending" | "continuing" | "resolved" | "cancelled" | "failed" | "uncertain"`), optional `verdict`/`admissions`/`risk_lane`, `uncertain`, and safe `uncertainty` explanations without `can_respond`, `can_redeliver`, raw `guidance`, `responder`, or action URLs. Risk-lane scope is computed strictly from recorded before/after snapshots (`liveIfNoAfterSnapshot: false`, never live working-tree walks): `risk_lane.scope` is `"recorded"` when both snapshots are present and verified, or `{ absence: "evidence unavailable", explanation }` with `unknown_scope: true` when recorded scope evidence is absent or incomplete. Operator text sanitization normalizes whitespace, replaces other control/bidi/zero-width characters with a visible `[ctrl]` marker, truncates on Unicode code points without splitting surrogate pairs, redacts whole path tokens starting with store/coordination/index/checkout/session/home paths, and conservatively scrubs generic absolute path-like tokens (starting with `/`, `~`, `file://`, or a drive letter) to `[redacted-path]`—meaning genuinely path-like question text is redacted. Empty healthy stores distinguish `absence: "not applicable"` (unmanaged) from `absence: "no records"` (managed), while missing `factory_managers` rows on an established factory with existing request rows still project those verified records and return `evidence: "unavailable"` / `absence: "evidence unavailable"` when empty or damaged; hot-journal, WAL, or unreadable stores return `{ factory_id, evidence: "unavailable", records: [], absence: "evidence unavailable", explanation }` without recovery.

Proposals (`GET /api/factories/:id/proposals`, rejecting any query parameter with HTTP 400 and unknown factories with HTTP 404) returns `{ factory_id, is_active_constraints_file: false, note: "Proposals are not the active constraints file.", evidence, records, ... }` so proposals are never presented as `.pi/constraints.json`. Each record projects `proposal_id`, `reference`, `action` (`"add" | "retire"`), `source`, `target_constraint_id`/`assigned_constraint_id`, bounded/path-scrubbed `text` (at most 512 code points, scrubbed of store/checkout/home/generic paths), `provenance` (`source`, scrubbed `run_id`, `attempt_id`, `evidence_ref`—marked `"not applicable"` for human-initiated retirements—optional scrubbed `note`, `proposed_at`, `decided_at`, optional `resolved_at`), `conflicting_ids`, `outcome` (`"pending" | "confirmed" | "rejected" | "dropped_duplicate"`, or `"unknown"` defensively for unexpected values), `file_sync_state` (`"pending_write" | "synced" | "conflict" | "abandoned"` when `confirmed`, `"unknown"` defensively for unexpected values, `{ absence: "evidence unavailable" }` if `confirmed` with missing sync state, or `{ absence: "not applicable" }` otherwise), and `uncertain`/`uncertainty` (set for unknown values or `"pending_write"`/`"conflict"`), omitting `canonical_checkout`, `decided_by`, `resolved_by`, raw `sync_error`, `can_confirm`, `can_reject`, `can_resolve_conflict`, and any action URLs. Empty healthy stores distinguish `"not applicable"` (unmanaged) from `"no records"` (managed); damaged rows, missing v12 proposal tables, hot-journal, WAL, or missing `factory_managers` on empty established factories return `evidence: "unavailable"` / `absence: "evidence unavailable"` without recovery.

The client assets (`factory/viewer/assets/{index.html,style.css,app.js}`) render all seven views directly from these snapshot shapes using `textContent`, `createTextNode`, and allowlisted attributes. Missing or incompatible data renders an explicit typed absence or HTTP error state rather than fabricated evidence.

## Read-only and privacy

The API is GET-only, accepts factory/version/reference identifiers rather than paths, and must be backed by configured state only. Never provide filesystem paths or arbitrary query parameters. The browser does not receive raw records, prompts, full briefs, logs, or store paths. Use fixture state only when verifying; do not use this viewer to test or operate a real factory.

## Manual acceptance checklist (not automated)

These five scenarios are intentionally manual; no browser DOM tests are used. None has been exercised in this implementation environment.

1. **Older bound version:** use a fixture with a verified v2 run and v3 current; confirm the graph uses v2 topology and configuration links stay in v2.
2. **Release evidence:** check known blockers and contradictory release evidence; reserved or failed-before-release launches must not be drawn as running.
3. **Connection failure and switch:** interrupt refresh during a run, then recover; verify Stale and last-good time, clear stale on recovery, distinguish fresh Uncertain, and switch factories without showing old data.
4. **Accessibility and layout:** keyboard-only navigate all views and node links; verify focus visibility, narrow drawer open/close (including Escape), semantic headings/tables, and textual status independent of color.
5. **Live refresh continuity:** refresh the same run and verify pan, zoom, selected node, expanded content, and keyboard focus remain; verify next verified run replaces ended state.

Additionally inspect browser network activity for local-only requests/no remote fonts, and against isolated fixtures with manager closed verify viewing all routes leaves state bytes unchanged. These are manual checks, not claims of verification.

# Publishing and inspecting software factory definitions (ticket 01)

`/factory list` discovers definitions, `/factory inspect <factory-id>` reads one immutable definition, and `/factory publish` opens an editor for JSON `{ "name": "quality", "draft": { ...bootstrap_generate request fields... } }`, validates the executable draft with Bootstrap's launch planner, and asks for an explicit human confirmation. Use only in a Pi session with a UI and a selected model when personas inherit that model. Publication creates `v1` with an opaque stable UUID; it does not create a run, resume management, activate admissions, or change standalone Bootstrap behavior. The `factory_inspect` tool shares the same operation boundary but accepts only `list` and `inspect`; it cannot publish.

The definition contains the canonical checkout path, resolved persona body, node instructions and contracts, graph edges, resolved model and thinking setting, resolved revision and first-attempt limits, cleanup/deadline settings, and resolved extension paths. When a persona selects a different explicit model, publication requires a thinking level that can be frozen from its declaration or model alias; it never saves `null` for that node to inherit a mutable Pi default. Persona tools are `declared` or `inherit`; skills are `declared` (including an explicitly empty list) or `inherit`. Extension policy records declared additions and paths while inherited Pi extensions remain a live runtime input. This record does **not** snapshot tool/skill availability, installed extension or skill contents, the Pi runtime, checkout contents, model-provider catalog/credentials, or any other live prerequisite. In particular a published, resolved model is not a promise that its provider is currently available or authenticated. Publication does not launch a worker or contact Herdr.

## Storage and interruption

Factory state lives in `factories.sqlite` beneath the isolated `PI_FACTORY_STATE_DIR`, otherwise the `PI_BOOTSTRAP_STATE_DIR`/Bootstrap session root (default `~/.pi/agent/bootstrap-sessions`). SQLite schema version 1 uses a single `BEGIN IMMEDIATE` transaction to write the complete definition and stable ID, `DELETE` journaling, and `synchronous=EXTRA`. The database file and every newly-created state-directory entry (including each parent directory entry) are synchronized before publication is acknowledged. Each stored definition is protected by a SHA-256 digest and validated as a v1 envelope on inspection; digest/envelope failures report corruption without changing the stored evidence. The first successful publication is `v1`; this ticket deliberately does not support editing, replacement, or later versions. The name is unique case-insensitively and a duplicate publication is rejected without altering the existing definition.

A definite validation or transaction failure rejects the publication. If a failure occurs after the commit boundary, the operation returns an explicit uncertain-outcome error rather than claiming success; use `/factory list` then `/factory inspect <factory-id>` to recover what committed, and do not retry with another name until reconciled. Read operations issue SQLite `query_only` transactions. SQLite may perform its documented hot-journal recovery while opening after an interrupted transaction; that is SQLite's storage recovery, not an application-level inspection repair or factory activation.

SQLite's journal and synchronization settings provide the usual local-filesystem commit contract: atomic transaction recovery and durable commit acknowledgement across process loss, reboot, and OS crash when the local filesystem and storage device honor synchronization/barrier requests and storage is intact and not rolled back. This is not proven against physical power removal by the process-kill test, and cannot protect against faulty hardware/filesystems, lost/rolled-back disks, malicious same-user modification, backups restored from an earlier point, or external effects. Process interruption testing alone does not establish those guarantees. No launch, submission, queue, manager, or intervention capability is included in this ticket.

# Factory cancellation, settlement and redelivery

## Cancel (`/factory cancel <factory-id>`)
Requires direct human confirmation bound to the exact target (input, attempt, run, bound version) and its consequences. Structured tools cannot supply the confirmation. Manager authority is rechecked after the dialog and again when the intent is committed. The cancel intent (`cancel.json`) is flushed to disk before `cancelled: true` is returned. Cancelling does not close tabs, prove settlement, undo effects or release either capacity hold. Direct `bootstrap_cancel`, force-close and cleanup stay rejected for factory-managed runs.

For a factory-managed run the dispatcher never writes a `cancelled` disposition on a node's behalf: only the worker's own record proves a node stopped. A node that reads as cancelled only because a cancel record exists is reported as unknown.

## Observations
Each attempt (`inspect`, `receipt`) shows four separate facts under `settlement`: `cancellation` (none / requested / unknown), `resource_closure` (closed only when the run's own record says every node resource closed, otherwise unknown: factory inspection never queries Herdr, so an externally closed tab is not seen), `execution_settlement` (settled / unsettled / unknown, with reason) and `capacity_release` (held / released). A failed run records outstanding attention in `settlement.attention`. `inspect` also lists `attention`: failed or partial runs, uncertain evidence, and a held run that cannot be released without operator clearance stay listed until resolved, so a missed notification never hides them. Inspection never settles, repairs or cleans up.

## Settlement (`/factory settle <factory-id>`; also tried first by `/factory launch`)
Both capacity holds are released, in one transaction, only when a fresh observation inside that transaction shows every node terminal and nothing cancelling, parked, working, pending or in error, with readable evidence. Cancellation, closed tabs, stale heartbeats or a reboot alone never settle a run; a normally completed run settles with tabs still open. On commit the attempt becomes `settled` (the settlement record, including when each hold was taken, is kept on the attempt so the deleted hold rows lose no history), the input becomes `settled`, both hold rows and the coordination run association are removed, and a worker waking on a settled run is refused. Suspected detached work (a node whose session was replaced by /new, /resume or /fork while no outcome was on record at that moment; recording cancellation during the teardown does not count, since a tool may still be running) and nodes still holding write ownership block settlement until stopped or isolated. Uncertain evidence never settles; clearance is a separate flow.

## Clearing an uncertain hold (`/factory clear <factory-id>`)
When a held run's evidence is missing or contradictory (an unreadable or contradicted run, input or association record; a cancelled run whose worker never acknowledged), settlement is refused and capacity stays held. `inspect` shows `clearance_eligibility` on that attempt: both holds and when each was taken, what is missing or contradictory, any `resume_risk`, and the exact action and consequences. The factory holds, it never guesses: affirmative evidence that conflicting work may still resume (a node still running, working, cancelling, parked, holding write ownership, or suspected detached) makes the hold not clearable at all, and confirmation, a reboot, a closed tab or cancellation intent cannot overcome it; stop or isolate that work first. A hold whose attempt is not durably fenced from release, or that does not own both holds, is not clearable either.

The command runs only in the managing, interactive Pi session. It shows the exact target, then collects from the human a confirmation, a reason, supporting evidence that the original work cannot resume, and an acknowledgement that past effects are unknown. The operation takes a human-confirmation function, never a flag, so a structured tool cannot supply any of it. After the dialog it re-checks the exact target, the managing authority and eligibility, and inside the commit transaction it re-observes the run, the holds and the identities that were shown.

One commit releases both holds, removes the coordination run association, retires the input (`cleared`, no longer launch-eligible) and records the attempt as `cleared` with a digest-protected `clearance` record: reason, evidence, acknowledgement, the evidence that was missing or contradictory, the input's prior disposition and the run's own settlement observations. Clearance is shown beside `settlement`, which keeps saying what the evidence said (typically `execution_settlement: unknown`), and `capacity_release: released`. It does not settle the run, rewrite its outcome, erase or repair any record, undo effects, or launch anything; a worker waking on a cleared run is refused. A cleared input is never replayed: identical resubmission returns the original receipt, and intentionally repeating it needs a new submission.

## Redelivery (`/factory redeliver <factory-id> <successor-node> [source-node]`)
Resends one handoff that nothing has claimed to a verified live destination, under the managing session's authority and without repairing or resuming the run. It reuses the standalone `retry_delivery` evidence rules; accepted or ambiguous handoffs are never replayed.

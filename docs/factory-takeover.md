# Factory management takeover

Opening `/factory inspect <id>` is read-only. To take over, use `/factory takeover <id>` in an interactive managing Pi session. The confirmation names the exact recorded manager incarnation; after confirmation, Pi rechecks its session binding and the durable operation rechecks that incarnation while holding SQLite's exclusive write transaction.

Manager identity is recorded as a random incarnation token plus the host boot ID, PID, and Linux `/proc/<pid>/stat` start-time ticks. If boot or process-start evidence is unavailable or malformed, management creation and takeover fail closed. A reboot proves the prior process cannot still run; on the same boot, a missing PID or a different start time proves the recorded process ended, while a matching PID and start time blocks takeover. PID alone and heartbeat age are never authority.

Successful takeover replaces the manager record atomically. The previous authority no longer passes mutation, launch, or release checks. Takeover does not cancel a run or clear the factory/checkout holds. For a retained attempt, inspect `/factory inspect <factory-id>` and proceed only when it reports affirmative `proven_not_released` evidence and retry eligibility; missing, damaged, contradictory, or release-claiming run/index manifests, release markers, holds, coordination records, or continuity anchors keep the holds in place and block retry. Retry with `/factory retry <factory-id> <input-id> <previous-attempt-id>` and confirm the displayed exact input and previous attempt. Retry preserves the accepted input, bound version, history, and FIFO position while creating a new attempt/request ID. It revalidates the proof and holds before reservation; do not edit evidence or use a status probe that generates a request. Standalone Bootstrap launches remain independent of factory coordination.

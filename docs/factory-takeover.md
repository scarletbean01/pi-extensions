# Factory management takeover

Opening `/factory inspect <id>` is read-only. To take over, use `/factory takeover <id>` in an interactive managing Pi session. The confirmation names the exact recorded manager incarnation; after confirmation, Pi rechecks its session binding and the durable operation rechecks that incarnation while holding SQLite's exclusive write transaction.

Manager identity is recorded as a random incarnation token plus the host boot ID, PID, and Linux `/proc/<pid>/stat` start-time ticks. If boot or process-start evidence is unavailable or malformed, management creation and takeover fail closed. A reboot proves the prior process cannot still run; on the same boot, a missing PID or a different start time proves the recorded process ended, while a matching PID and start time blocks takeover. PID alone and heartbeat age are never authority.

Successful takeover replaces the manager record atomically. The previous authority no longer passes mutation, launch, or release checks. Takeover does not cancel a run or clear the factory/checkout holds. It also idempotently retires any leftover `coord.managed_runs` rows belonging to verified terminally superseded `proven_not_released` attempts of that factory (where a later attempt of the same input is already `settled` or `cleared` with `release_authorized = 1`, no hold references the old attempt, and full non-release evidence remains intact), without ever retiring or weakening uncertainty on mismatched or damaged evidence. For a retained attempt, inspect `/factory inspect <factory-id>` and proceed only when it reports affirmative `proven_not_released` evidence and retry eligibility; missing, damaged, contradictory, or release-claiming run/index manifests, release markers, holds, coordination records, or continuity anchors keep the holds in place and block retry. Retry with `/factory retry <factory-id> <input-id> <previous-attempt-id>` and confirm the displayed exact input and previous attempt. Retry preserves the accepted input, bound version, history, and FIFO position while creating a new attempt/request ID. It revalidates the proof and holds before reservation; do not edit evidence or use a status probe that generates a request. Standalone Bootstrap launches remain independent of factory coordination.

The reservation transaction also inserts an immutable `factory_run_indexes` association in the holder's factory database. Its version-tagged digests bind the exact task, factory, input, attempt, request, bound version, physical checkout, both database paths, and original canonical Bootstrap index root. Non-release validation reads that verified route, then reads the original raw request reservation and indexed manifest plus local manifest/sidecar/release evidence. An observer's cwd, factory database directory, Bootstrap index, or editable sidecar cannot select a replacement route. This also permits re-inspection and takeover from a different Bootstrap root without recreating the original request.

The association table is an additive extension of factory schemas v4/v5; existing row digests, release readers, ticket 01/02 storage and standalone records are unchanged. It is created only during a new reservation, with no backfill or guessed route for earlier attempts. Missing legacy associations, mismatched identity/digest, or damaged original evidence retain the holds and never prove non-release or authorize retry.

`takeover` (like `settle_run` and `clear_hold`) only includes optional `retirement_diagnostics?: Array<{ attempt_id: string; task_id: string; reason: string }>` when an already-superseded `proven_not_released` attempt (one with a later terminal `settled`/`cleared` sibling) has a leftover `coord.managed_runs` row whose non-release or structural evidence failed verification so the row was retained. Normal `proven_not_released` rows waiting for retry do not populate `retirement_diagnostics`.

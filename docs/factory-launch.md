# Launching the first input safely (ticket 03)

## Command and authority surface

- `/factory launch <factory-id>` (interactive managing Pi session with UI only; blocked in Bootstrap worker sessions, non-UI modes, and untrusted projects): takes the oldest eligible input at the head of the factory's FIFO queue (the first input still waiting in acceptance order; an active run's input is not the head, and a blocked or retryable waiting input is never skipped) and launches one Bootstrap run into the managing pane's Herdr workspace (`HERDR_ENV=1`, `HERDR_PANE_ID` via `herdr pane get`, never the focused workspace).
- An explicitly resumed or taken-over manager watches its factory queue and periodically tries only its current head. This is scheduling, not inspection: it invokes the same fenced launch operation, and any preflight/version/uncertainty/checkout blocker remains on that head. A completed run's holds are released by the existing proven-settlement path in launch; no tab closure, notification or inspection is treated as settlement. The manager watch ends when its session shuts down or its authority is revoked.
- No model tool, chat message, startup hook, `/factory inspect`, `/factory receipt`, or un-managed session launches a run. `factory_inspect` remains read-only (`list`, `inspect`, `receipt`).
- **Retained executable definition:** Launch consumes only the integrity-verified retained definition of the exact version bound to the FIFO head at admission (`v1` or a later retained version; never the draft, the current pointer or any other version) (target checkout, topology, nodes, contracts, dependencies, ownership, persona system prompts, resolved model/thinking, declared tools/skills/extensions, limits). Changes to `.pi/agents/*.md`, `modelAliases`, or `graph.defaults` after admission do not alter queued inputs. Live prerequisites (`project_cwd`, writable `.pi/agent-sessions`, `coms_extension`, retained extension paths, `worker.ts`, `pi` and `herdr` on `PATH`, `required_artifact_paths` publication checks, and live `graph.ceilings` in `bootstrap.json`) are checked at launch and fail closed, blocking the FIFO head without skipping or substituting.
- **Project trust, physical checkout identity, and session incarnation fencing:** Both live session authority (`session_shutdown`, session ID/file binding, `factory_managers`) and project trust (`ctx.isProjectTrusted()` plus `trust.json` / target checkout verification), plus the checkout's resolved canonical path and physical `(dev, ino)` identity (`checkout_key` from `statSync(..., { bigint: true })` on `realpathSync(project_cwd)`), are checked at launch start, before reservation commit, and synchronously right before release authorization with zero `await` gap between the final fence, the SQLite release commit, and exclusive `release.json` publication.
- **Immutable task input and bounded brief:** The accepted brief is preserved verbatim (including multiline CRLF/CR/LF, tabs, leading/trailing spaces/newlines, control characters, unicode, and up to 16 KiB UTF-8) in `${session_dir}/${input_key}.input.json` (where `input_key` is `${instance}.1` for review-plan runs or `${instance}`, protected by `input_hash`, retrievable via `bootstrap_read_input({ kind: "task_input" })`). Worker prompts embed only a bounded excerpt (`BRIEF_FIELD_MAX_BYTES = 2048`) plus pointer and treat the brief strictly as literal untrusted input, never as plan data or paths. Factory-managed workers require this non-symlink regular file, validate its identity and `input_hash` via `parseTaskInput`, and verify that `submitted_brief` matches the authoritative accepted brief/digest from the validated SQLite release proof before passing release, before admission/model work, and on `bootstrap_read_input({ kind: "task_input" })`, failing closed without falling back to worker config fields if missing, malformed, symlinked, or mismatched.

## Cross-storage ordering, coordination, and release gate

1. **Pre-launch checks & Herdr workspace lookup:** Live preflight, authority/trust, and `herdr pane get <HERDR_PANE_ID>` run before any capacity hold is committed.
2. **Atomic multi-DB reservation (`factories.sqlite` + `factory-coordination.sqlite`):**
   - `factories.sqlite` lives in `PI_FACTORY_STATE_DIR` (or `PI_BOOTSTRAP_STATE_DIR`, defaulting to `~/.pi/agent/bootstrap-sessions`).
   - Host-wide checkout coordination lives in `factory-coordination.sqlite` in `~/.pi/agent` (OS account home via `BootstrapService`'s `home` option, independent of `PI_CODING_AGENT_DIR` profiles, `PI_FACTORY_STATE_DIR`, and `PI_BOOTSTRAP_STATE_DIR`), with `PI_FACTORY_COORDINATION_DIR` accepted only for explicit test isolation.
   - A companion continuity anchor (`factory-coordination.sqlite.anchor.json` paired with `coord_meta` inside the DB) prevents treating a missing or replaced previously initialized central coordination DB as a clean slate across state roots.
   - Both databases use SQLite `DELETE` journal mode, `synchronous = EXTRA`, symlink-free physical paths (`lstat` across all path components), and fsynced directory ancestry.
   - Inside a single `BEGIN IMMEDIATE` transaction attaching `factory-coordination.sqlite` as `coord` (using SQLite's rollback super-journal protocol across both DBs), the launcher verifies schema/continuity/manager/queue/hold integrity (factories schema v4 or v5, coordination schema v2; every release gate, the failure recorder and the worker-side release reader accept exactly those schemas and, for v5, re-verify the retained bound version row; earlier path-only launch records fail closed without silent rekeying or clearance while ticket 01/02 v1/v2 reads and admissions remain supported) and checks both the factory slot (`factory_holds`) and checkout-scoped central evidence (`coord.checkout_holds` and `coord.managed_runs` by both `canonical_checkout` and physical `checkout_key`, failing closed across factories on orphaned/contradictory records, directory renames, or path replacement while keeping unrelated checkouts isolated), then atomically commits:
     - `factory_inputs.disposition = "launching"`
     - `factory_attempts` (`attempt_id`, `bound_version`, `request_id`, `task_id`, `canonical_checkout`, `checkout_key`, `state = "reserved"`, `release_authorized = 0`, SHA-256 `record_digest`)
     - `factory_holds` (factory slot hold)
     - `coord.checkout_holds` (host-wide hold unique on both `canonical_checkout` and `checkout_key`)
     - `coord.managed_runs` (`task_id`, `request_id_digest`, `canonical_checkout`, and `checkout_key` association)
3. **Synced Bootstrap run preparation:** `ensureSessionDir(..., durable=true)` syncs `.pi`, `.pi/agent-sessions`, and `sessionDir` directory entries. `manifest.json`, `index/${task_id}.json`, `factory-run.json`, `index/factory-runs/${task_id}.json`, `request-${requestKey}.json`, `upstream-index.json`, `${instance}.input.json`, `${instance}.config.json`, and `${instance}.sh` are written via `open("wx")` + `fsync` + `rename`/`link` + parent directory `fsync`.
4. **Herdr launch & readiness wait:** Tabs/panes are created in the managing pane's workspace and workers acknowledge readiness while blocked at the release barrier.
5. **Affirmative release authorization before worker action:**
   - After readiness checks pass, the launcher synchronously verifies session authority, project trust, checkout canonical path + physical `checkout_key`, full identity/run/hold/`coord.managed_runs` agreement (matching what workers check), and via `lstatSync` that no existing entry (including a broken symlink or non-`ENOENT` path error) occupies `release.json` right before commit, generates a fresh release-publication-specific `release_nonce` (never stored in pre-release manifests or worker configs), and commits `release_authorized = 1`, `release_token_digest = sha256(manifest.token)`, `release_nonce_digest = sha256(release_nonce)`, `state = "released"`, and `factory_inputs.disposition = "running"` across `factories.sqlite` and `coord` in one `BEGIN IMMEDIATE ... COMMIT` super-journal transaction.
   - Immediately (with no `await` gap), after rechecking physical checkout identity (`resolveCheckoutIdentity`) post-commit (failing as `uncertain` without publishing if replaced), managed `release.json` (carrying plaintext `factory_managed.release_nonce`) is published exclusively via `publishExclusive` (`open("wx")` temp + `fsync` + exclusive `link` + directory `fsync`) so any post-commit racing entry (even one reusing pre-release identifiers) is never overwritten and never validates against `release_nonce_digest`. Failures after release commit (including `EEXIST` conflict or failure after `link` before directory `fsync`) never write `abort.json`, roll back committed SQLite proof, or falsely declare pre-release failure; they record `status: "error"`, `phase: "uncertain"`, and reject the launch acknowledgement. Standalone runs retain `atomicJson` release publication. Failures before release commit write `abort.json` without `release.json` and record `failed_before_release` on the attempt and holds (fencing the SQLite release gate); when `abort.json`, intact non-release run/index/request/hold evidence, and verified exit of every node that acknowledged readiness (no live `ready.json` process and no `.pgid.json`/`.result.json`) all hold, the managing session records `proven_not_released` automatically (or via `/factory settle` / the queue watcher once remaining ready nodes exit) so `/factory retry` can proceed without takeover, while missing/damaged/contradictory evidence or live ready nodes keep the holds blocked.
   - `bootstrap/worker.ts` refuses to pass the release barrier or admit unstarted work at its pre-turn admission fence unless both `release.json` (verified on a symlink-free physical path as an `lstat`-checked regular file opened with `O_NOFOLLOW | O_NONBLOCK` before any read) AND `factories.sqlite` + `factory-coordination.sqlite` (`PRAGMA query_only = ON`) prove `release_authorized = 1`, matching `release_token_digest`, matching `release_nonce_digest`, matching `factory_holds`, `coord.checkout_holds`, `coord.managed_runs`, `checkout_key`, run-local `manifest.json` (non-symlink regular JSON with matching concrete `task_id`, non-empty `token`, `project_cwd`, `session_dir`, and normalized `factory_managed` identity), and `factory-run.json`, followed by a final worker-side physical checkout identity check before passing release (without invalidating already-admitted work). The shared release reader (`bootstrap/factory-evidence.ts`) validates all five persisted SQLite rows (`factory_attempts`, `factory_inputs`, `factory_holds`, `coord.checkout_holds`, and `coord.managed_runs`) using the exact same row-digest and invariant validators (`bootstrap/factory-records.ts`) as launch/operations.
   - Read-only inspection validates both own and cross-root holder release proof (`release.json` JSON/token/identity, run-local `manifest.json`, `factory-run.json`, and the holder's own authoritative `factories.sqlite` + `factory-coordination.sqlite` rows) via the shared release reader without repairing or deleting invalid markers — including during active owner launches (preserving `launching` only for validated `held`/`released` proof or an active-lock committed run awaiting `release.json` publication) — treating `session_dir_removed` claims as unable to bypass required release/local evidence while preserving legitimate pre-release interruption holds, and propagating release-evidence uncertainty to `attempt.run`, `uncertainty`, capacity slots, and `head_status` (while avoiding nested SQLite reads inside reservation writer transactions).

## Read-only inspection and direct run mutation guards

- `/factory inspect`, `/factory receipt`, `factory_inspect`, `BootstrapService.status`, `statusWithCleanup`, `waitForStatus`, `recover({ action: "inspect" })`, `SessionStore.list`, and graph widgets are strictly read-only for factory-managed runs: no launch repair, no `reconcile(..., persist=true)`, no status-triggered `disposition.json` writes, no automatic cleanup, and no timeout-triggered cancellation.
- Direct `bootstrap_generate` replay of a factory `request_id`, `bootstrap_cancel`, `bootstrap_cleanup` (including `delete_session_files`), `bootstrap_recover` (`retry_delivery`, except the factory-authority redelivery in [factory-settlement.md](factory-settlement.md)), and the persisted `bootstrap_report` service path (`report.json`/`report.md`, explicit `results`, reconciliation) reject on factory-managed runs — including across alternate `PI_BOOTSTRAP_STATE_DIR` roots and when ancillary metadata (`factory-run.json`, `factory_managed`) is missing, stripped, or corrupted. `bootstrap_report` with only a `task_id` on a factory-managed run instead returns a read-only report that writes nothing (see [factory-versions.md](factory-versions.md#reporting-on-factory-managed-runs)).
- Capacity holds stay conservative across uncertainty. They are released on reliable execution settlement only (see [factory-settlement.md](factory-settlement.md)); there is still no auto-clear of uncertain holds, no replay, and no autonomous progression. Missing or contradictory evidence is surfaced in `inspect` (`capacity.* = "uncertain"`, `uncertainty` reasons) without exposing authority secrets.

## Durability boundary and limitations

- All SQLite commits use `DELETE` + `synchronous = EXTRA` + `ATTACH` super-journal transactions over symlink-rejected physical paths with fsynced directory ancestry, and Bootstrap launch/release files and directories are explicitly `fsync`ed.
- On Linux local filesystems (`ext4`, `xfs`, etc.) with barrier/flush support enabled, this provides atomic crash recovery across process termination (`SIGKILL`), Herdr loss, ordinary reboot, and OS crash when local storage is intact and not rolled back.
- **Physical identity and testing limitations:** Physical checkout contention relies on local POSIX `(dev, ino)` identity (`statSync` with `bigint`) paired with `canonical_checkout` and the local OS-account coordination root. It detects symlink aliases, directory renames, and directory replacement at the original path on intact local filesystems with stable device/inode numbers, without blocking unrelated checkouts when a held directory is renamed. It does not coordinate across separate hosts, distinct bind/overlay mounts with different `st_dev` (or filesystems without stable inode numbers), or deleted-and-reallocated inodes after an uncoordinated filesystem rebuild. Supervised `SIGKILL` tests verify SQLite rollback, super-journal atomicity, cross-storage ordering, and post-commit survival across process loss; they do **not** by themselves prove physical power-loss durability if underlying disk write caches, mount options (`nobarrier`), network filesystems (NFS), or virtualized storage ignore or reorder `fsync`/barrier requests. Same-user malicious writes, disk corruption beyond local checksums, and undisclosed background side effects of arbitrary worker tools are outside the guarantee.
